# 第 07 课：模块边界 —— 判定为什么不能写在 executor 里

**目标**：理解这个项目的分层，以及分层是用来防什么的。

## 1. 分层

```text
main.rs      只分发命令
lib.rs       串联四步
  ├─ plan.rs        读配置 + 校验
  ├─ builder.rs     展开单元
  ├─ executor.rs    执行，产出测量值
  │    └─ rate_window.rs   算有效平均
  ├─ verdict.rs     判定规则（唯一一份）
  └─ report.rs      渲染 + 落盘
```

## 2. 一条铁律：判定只有一份

`executor.rs` 的模块注释写着：

> 它**不自己判定**。判定规则全在 `crate::verdict`。

`report.rs` 的模块注释写着：

> 它**只渲染，不判定**。`verdict` 字段是执行侧算好写进来的。

这不是洁癖。真实项目的 `src/verdict.rs` 开头记着这段教训：

> 判定规则曾经在 `master::executor`（执行侧聚合）和 `report`（报告侧回退聚合）
> 各实现一遍，两份实现的优先级顺序不一致，先后产生过两个真实缺陷：
> 概览把「必须灌通的方向硬失败」显示成另一方向普通的 `NOT_EVALUATED`；
> TCP/CTS 路径先判 `RX_BELOW_TARGET` 再检查采样是否可信，把环境异常写成了
> CPE 性能失败。

**两份实现最终一定会漂。** 不是"可能"。

## 3. 聚合优先级

`verdict.rs::aggregate_verdict`：

```text
空          → SetupError
任一 SetupError → SetupError
按 [RateFail, NotEvaluated, Measured] 顺序取第一个命中
任一 Skip   → Skip
否则        → Pass
```

**`Pass` 在最后**。反过来写（先看有没有 Pass）会让一条腿通过就盖住另一条腿的失败 ——
双向测试里这意味着"下行好、上行断"被报成"通过"。

## 4. 依赖方向

```bash
grep -rn "^use crate::" src/
```

你会看到依赖是单向的：`executor` → `verdict`、`rate_window`，
但 `verdict` 不依赖任何别的业务模块，它只认 `reason`。

**越核心的模块依赖越少。** `verdict.rs` 不知道 iperf、不知道网卡、不知道报告长什么样，
所以它最好测、最稳定，也最不容易被别的改动带坏。
