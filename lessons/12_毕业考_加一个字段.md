# 第 12 课：毕业考 —— 把一个字段从配置传到报告

**这一课没有标准答案。做完它，你就具备维护 cpe-test 的最小能力了。**

## 任务

给计划加一个 `note` 字段（这条测试的备注），让它一路传到报告里：

```json
{
  "title": "TCP-A",
  "transport": "tcp",
  "note": "客厅，隔一堵承重墙"
}
```

```bash
cargo run -- demo
```

```text
测试项                        实测速率      门限          结果
TCP-A                         950 Mbps      900 Mbps      PASS
  备注：客厅，隔一堵承重墙
```

并且存进 `rows.jsonl`，`cargo run -- report` 读回来还能看见。

## 要求

1. `note` 是可选的，**不填不能报错**（旧计划文件必须照常能读）
2. 双向单元的两条腿共享同一个 note
3. `note` **不参与判定** —— 加了它之后所有判定结果必须和加之前一模一样
4. 至少两个测试：一个验证 note 传到了报告，一个验证不填时不出错
5. `cargo test` 全绿

## 做之前先想清楚

这个字段要经过哪几层？

```text
plan.json → Spec → Unit → UnitOutcome → Row → 渲染
```

每一层都要改吗？想清楚再动手。**改的层数越少越好** ——
如果你发现要改 6 个文件，先停下来想想是不是有一层可以跳过。

### 一条可以照着走的路线（不是答案，是方法）

**从终点往回推，而不是从起点往前铺。**

1. 先问：**最后要在哪看到它？** —— `render()` 打出来的那一行
2. 再问：`render()` 从哪拿数据？—— `Row`。所以 `Row` 要有这个字段
3. 再问：`Row` 从哪来？—— `rows_from(&outcomes)`。所以 `UnitOutcome` 要有
4. 一直问到 `plan.json`

这样走一遍，每一层「要不要改」都有明确理由，不会漏也不会多改。

**反过来从 `plan.rs` 开始加，很容易加着加着发现中间某一层其实用不上** ——
但那时候已经改完了，你也不会再把它删掉。

### 先写测试，还是先改代码？

**先写一个会失败的测试。**

```rust
#[test]
fn note一路传到了报告() {
    // 现在编译不过（Spec 还没有 note 字段）——这正是起点
}
```

编译不过的地方，就是你接下来要改的地方。
编译器会**一层一层**带着你走完整条链路，比你自己列清单可靠。

这就是所谓「让编译器当向导」：在 Rust 里加字段、改类型，
跟着报错走通常比事先设计得更快也更全。

## 做完之后回答

写下来，不要只在脑子里过：

1. **你改了哪几个文件？为什么是这几个？**
2. **有没有哪一层你本来以为要改，结果不用改？为什么？**
3. **如果这个字段将来要参与判定（比如 note 里含「实验」就跳过判定），
   你要改的是同样这几处吗？**
4. **你的测试在哪种情况下会失败？** 如果答不上来，说明那个测试没测到东西。

## 验收

```bash
cargo test
cargo run -- demo
cargo run -- report output/rows.jsonl
cargo run -- run fixtures/plan_edge.json   # 这份没有 note，必须照常能跑
```

- [ ] 有 note 的显示出来，没 note 的照常跑
- [ ] 所有判定结果和改动前完全一致
- [ ] `cargo test` 全绿
- [ ] 四个问题都能回答

### 怎么证明「判定结果和改动前完全一致」

第 3 条要求听起来不好验 —— 难道要人眼对着两份输出比？

不用。**第 20 课的黄金文件就是干这个的**，哪怕你还没做那一课，现在也能用：

```bash
cargo test --test golden
```

改完之后它一定会红 —— 因为渲染出来多了一行备注。这时候：

```bash
UPDATE_GOLDEN=1 cargo test --test golden
git diff fixtures/golden/
```

**看那个 diff。** 如果它只多出了备注那几行，别的一个字没变，
那就证明判定没被你动过。要是哪个 `PASS` 变成了 `NOT_EVALUATED`，
diff 会当场把它摆在你面前。

> 「我改动的影响范围到底有多大」——
> 这个问题在真实项目里最难回答，也最值钱。
> 黄金文件把它变成了一条 `git diff`。

## 为什么是这个任务

这正是 45 天路线里的那条目标：

> 能增加一个简单字段并完成前后端联动

在真实 cpe-test 里，同一个字段要多走 3 层：
`Vue → TypeScript → HTTP → Rust DTO → builder → executor → verdict → report`。
这里少了前三层，但**后面的链路是一样的**。

在这里做一遍，你就知道到了真实项目该沿着哪条路找。

## 做完之后

回到 `cpe-test`，挑一个真实的简单字段（比如
`Row` 里的 `kind_label`），**只读不改**，从 `Row` 一路往回找到它的来源。
能找到，就说明这套方法你已经会用了。
