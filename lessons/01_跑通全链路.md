# 第 01 课：跑通全链路，看懂入口

**目标**：让程序跑起来，并且能说清一条命令是怎么走到业务函数的。

## 1. 先跑

```bash
cd cpe-mini
cargo run -- demo
```

你会看到三种结果：`PASS`、`RATE_FAIL`、`NOT_EVALUATED`。

再把六个命令都跑一遍，**先不管它们内部在干什么**，只看输入和输出：

```bash
cargo run -- plan fixtures/plan.json      # 只展开，不执行
cargo run -- report output/rows.jsonl     # 读回报告重新渲染
cargo run -- csv output/rows.jsonl        # 导出给 Excel
cargo run -- compare 旧.jsonl 新.jsonl     # 两轮对比
cargo run                                  # 不给命令 → 打印用法
cargo run -- 乱敲                          # 不认识的命令 → 提示 + 用法
```

最后两个也要跑。**一个程序在你用错的时候怎么表现，和它正常时怎么表现一样重要** ——
这是这个项目刻意在教的东西之一。

## 2. 读代码：`src/main.rs`

只看这个结构：

```rust
fn main() {
    let args: Vec<String> = std::env::args().skip(1).collect();
    std::process::exit(real_main(args));
}

fn real_main(args: Vec<String>) -> i32 {
    let mode = args.first().map(|s| s.as_str()).unwrap_or("");
    match mode {
        "demo" => ...,
        "plan" => ...,
        "run" => ...,
        "report" => ...,
        other => ...,
    }
}
```

三个要点：

1. `args().skip(1)` —— 第 0 个是程序自己的路径
2. `main` 自己不干活，把退出码交给 `real_main`，每个分支明确返回 0 还是 1
3. `match mode` 是整个程序的**分发中心**

### 顺手学一个查代码的手法

真实项目 7.6 万行，你怎么知道 `cargo run -- ui` 从哪开始跑？

**搜那个字符串字面量。**

```bash
grep -rn '"ui"' src/
```

命令名、配置键、原因码、JSON 字段名 —— 这些**字符串常量是最好的路标**，
因为它们在代码里只会出现在一两个地方，而且一定在真正处理它的那一行附近。

比顺着函数调用一层层点进去快得多。试试：

```bash
grep -rn '"compare"' src/
```

一行就定位到了 `main.rs` 里那个分支。

## 3. 全链路

```text
plan.json
  → plan::load           读配置 + 校验
  → builder::build_units 展开成测试单元
  → executor::execute_plan  执行
      ├─ rate_window::effective_rx_avg  算有效窗口平均
      └─ verdict::rate_verdict          判定
  → report::rows_from / write_jsonl / render
                                │
                         rows.jsonl 存下来之后还有两个出口：
                                ├─ compare   两轮对比（第 15 课）
                                └─ to_csv    导出 Excel（第 17 课）
```

`src/lib.rs` 的 `run_plan_cancellable()` 就是把这四步串起来，一共四行。先看它。

**四步的顺序不是随便排的**：每一步的输出正好是下一步的输入，
而且**中间任何一步都能单独拿出来测** —— 这是这个项目最值得学的结构。

### 一条建议：先看形状，别抠细节

第一次读一份陌生代码，目标是**画出它的形状**，不是读懂每一行。

具体到这个项目，`README.md` 里有一张「代码导读顺序」表，
按**从简单到复杂**排好了 11 个文件。照着读，读不懂就跳过往下走。

> 整体形状比某一行细节重要。形状对了，细节哪天需要再回来抠。

## 4. 动手任务

1. 在 `real_main` 里加一个 `"version"` 分支，打印 `cpe-mini 0.1.0` 并返回 0
   （版本号别手写，用 `env!("CARGO_PKG_VERSION")` 从 `Cargo.toml` 里取 ——
   手写的那个迟早和真实版本号对不上）
2. 在 `help()` 里加上这一行。**加了分支不加用法，等于没加**
3. 故意把 `"demo"` 写成 `"demoo"`，跑 `cargo run -- demo`，看会走到哪个分支
4. 用 `grep -rn '"csv"' src/` 找到 csv 命令的处理位置，看它调了哪个函数

## 5. 验收

```bash
cargo run -- version
cargo run -- 乱敲 ; echo "退出码=$?"
cargo test
```

- [ ] `version` 能跑，退出码 0
- [ ] 不认识的命令给提示 + 用法，退出码 1
- [ ] `cargo test` 全绿（111 个测试）
- [ ] 能画出 `cargo run -- demo` 走过的完整调用链
- [ ] 会用 `grep -rn '"compare"' src/` 这个手法定位一个命令

打开 `src/main.rs`，看第 40、54、56 行。

`compare` / `scan` / `monitor` / `ui` …
