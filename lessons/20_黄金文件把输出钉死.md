# 第 20 课：黄金文件 —— 把「给人看的输出」逐字钉死

前面那近百个测试都在问同一种问题：**这个值对不对**。

它们管不了这件事：

> 有人给 `render` 的表头多加了两个空格，或者把「无有效数据」改成了「N/A」。
> 所有断言照样全绿 —— 因为没有一条断言提到过表头。

而下游的脚本、Excel 模板、贴进周报的截图，全都认那个格式。

**报告的排版是对外兼容面**，和第 03 课那个 `"RATE_FAIL"` 大写串是一个性质。

---

## 1. 先跑

```bash
cargo test --test golden
```

```text
running 6 tests
......
test result: ok. 6 passed
```

这六个测试干的事很简单：跑一份计划，把渲染出来的整段文本，
和 `fixtures/golden/` 里存好的文件逐字比对。

打开一个看看：

```bash
cat fixtures/golden/plan.render.txt
```

就是 `cargo run -- demo` 打出来的那一段，存成了文件。

## 2. 故意改坏它

打开 `src/report.rs`，找到 `render` 里那个「无有效数据」，改成 `N/A`。

```bash
cargo test --test golden
```

```text
输出和 fixtures/golden/plan.render.txt 对不上。

第 7 行：
  黄金文件：TCP-C                         无有效数据    900 Mbps      NOT_EVALUATED
  这次跑出来：TCP-C                         N/A           900 Mbps      NOT_EVALUATED

改动是故意的就更新它：
    UPDATE_GOLDEN=1 cargo test --test golden
然后 git diff fixtures/golden/ 看一眼变了什么。
```

**哪一行、原来是什么、现在是什么** —— 一次说清。

改回去，再跑一次，绿。

## 3. 改动是故意的怎么办

假设你真的想把它改成 `N/A`。那就认可这次改动：

```bash
UPDATE_GOLDEN=1 cargo test --test golden
git diff fixtures/golden/
```

```diff
-TCP-C                         无有效数据    900 Mbps      NOT_EVALUATED
+TCP-C                         N/A           900 Mbps      NOT_EVALUATED
```

**这个 diff 就是你这次改动对用户可见的全部影响。**

这是黄金文件最值钱的地方，比"防止改坏"更值钱：

> 你改了一行判定逻辑，`git diff fixtures/golden/` 告诉你
> 报告里有三处跟着变了 —— 其中两处你根本没想到。

改逻辑的人通常只想着自己改的那一处。黄金文件把**所有**下游影响摊开给你看。

## 4. 时间戳：先脱敏，不然测试永远是红的

`Row.time` 是 unix 时间戳，每秒都不一样。直接存进黄金文件，
下一秒就对不上了。

所以 `tests/golden.rs` 里有这个：

```rust
fn normalize(text: &str) -> String {
    // CSV 的第一列是 unix 时间戳，换成 <TIME>
}
```

导出来的 CSV 黄金文件长这样：

```text
<TIME>,demo-0-r1,demo-0-r1,TCP-A,tcp,tcp / ab / 900 Mbps,PASS,COMPLETED,...
```

> **一个总是红的测试等于没有测试。** 红成常态之后就没人看它了，
> 真的坏了也不会有人发现。

但脱敏要**脱得尽量少**。换掉的每一处都是「这里将来变了也不会有人发现」。
这个项目只换了一样东西，因为它只有一样东西是不稳定的 ——
这也是「模拟执行、不起进程」这个设计换来的好处。

常见要脱敏的还有：文件路径（机器不一样）、随机 ID、耗时（毫秒数）、
主机名。每多一个，测试的价值就少一分 —— 所以真正的解法往往是
**让程序的输出别那么随机**。

## 5. 六个用例分别钉住什么

| 黄金文件 | 钉住的东西 |
|---|---|
| `plan.render.txt` | 三种典型结果的表格排版 |
| `plan_edge.render.txt` | 五种边界情况的措辞 |
| `plan_loss.render.txt` | 丢包诊断那一段（第 16 课） |
| `plan.csv` | **列顺序**和转义（第 17 课） |
| `compare_v1_v2.txt` | 对比报告的排序和分组（第 15 课） |
| `plan_bidir.cancelled.render.txt` | 被取消的单元还在不在（第 18 课） |

最后一个特别值得说：它钉的不是排版，是**行数**。
第 18 课那条「取消之后剩下的单元不许从报告里消失」，
在这里有了一份**逐字**的证据 —— 有人把 `execute_plan_cancellable` 改回
`break`，这个文件立刻从六行掉到两行。

> 好的黄金文件不只是「格式没变」，它顺带钉住了一批很难用断言表达的规则。

## 6. 什么时候**不该**用黄金文件

- **值的对错**。「RX 平均等于 950.3」用 `assert_eq!` 表达得更清楚，
  失败信息也更好读。黄金文件是给「一整段输出」用的。
- **输出很长**。三百行的黄金文件没人会认真读 diff，
  更新时会直接 `UPDATE_GOLDEN=1` 了事 —— 那就退化成了橡皮图章。
- **输出不稳定**。要脱敏五处以上，说明该先去修程序。

**黄金文件不能替代断言，它补的是断言够不着的那一层。**

## 7. 动手任务

### 任务 A：加一个用例

`fixtures/plan_bad.json` 是语义非法的配置，报错一次报四个问题。
那段报错也是给人看的，也该钉住。

在 `tests/golden.rs` 里加一个测试，把 `plan::load` 的错误信息存成
`fixtures/golden/plan_bad.error.txt`。

提示：`load` 返回的是 `Err(String)`，不是 `Row`。

### 任务 B：让它抓一次真的

1. 跑 `cargo test --test golden`，绿
2. 改 `src/verdict.rs` 里 `rate_verdict` 的措辞（比如把 `>=` 改成 `不低于`）
3. 再跑，看它报哪几个文件
4. `UPDATE_GOLDEN=1 cargo test --test golden` 然后 `git diff fixtures/golden/`
5. `git checkout fixtures/golden/ src/verdict.rs` 还原

第 3 步会有惊喜：**改一个地方，通常不止一个黄金文件变**。

### 任务 C（难）：防住橡皮图章

`UPDATE_GOLDEN=1` 太好按了。想一个办法，让「没看 diff 就更新」变难一点。

（没有标准答案。真实项目常见的做法有：把黄金文件加进 code review 的
必看清单、更新时要求写一行理由、CI 上禁用这个环境变量。
挑一个说说它挡得住什么、挡不住什么。）

## 9. 对应真实项目

`cpe-test` 的 `src/report/` 有一批同样思路的测试，钉的是 xlsx 的列顺序
和 HTML 对比报告的结构。

真实项目还多一件这里没有的事：**跨版本的报告要能互相读**。
v6.3 存下来的 `rows.jsonl`，v6.4 的 `report` 命令要能打开。
黄金文件于是兼做「格式没变过」的证据 ——
`fixtures/` 里留着几份旧版本的报告，每次发版都要能读回来。

这和第 17 课那句「列顺序是对外兼容面」是同一件事的两种说法：
**一旦有人依赖了你的输出格式，那个格式就是 API。**
