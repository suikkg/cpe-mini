## 1. 先看一个双向单元

一个双向测试单元有两条腿：A→B 和 B→A。两条腿各有各的判定，
最后要合成**一个**单元结论。合成规则就是 `aggregate_verdict`。

现在的规则很简单，优先级从高到低：

```text
空 → SETUP_ERROR
任一 SETUP_ERROR → SETUP_ERROR
按 [RATE_FAIL, NOT_EVALUATED, MEASURED] 取第一个命中
任一 SKIP → SKIP
否则 → PASS
```

注意 `RATE_FAIL` 排在 `NOT_EVALUATED` 前面。看一眼这个组合：

| A→B | B→A | 单元结论 |
|---|---|---|
| `RATE_FAIL`（RX 850 < 门限 900） | `NOT_EVALUATED`（采样覆盖率 12%） | **`RATE_FAIL`** |

**这个结论是错的。**

两条腿跑在同一段时间窗里。B→A 那边采样塌了 —— 说明那段时间网卡计数器
就没正常工作。那 A→B 测出来的 850 Mbps 凭什么可信？

拿它判 `RATE_FAIL`，就是把**环境异常写成了 CPE 性能失败**。
这正是整套判定规则一直在防的那个方向。

## 2. 第二条特例：`blocks_other_legs`

所以真实项目在 `RATE_FAIL` 前面插了一步：

```text
3. 任一「会盖住别的腿」的 NOT_EVALUATED → NOT_EVALUATED
```

「会盖住别的腿」是什么意思？不是所有的「判不了」都该盖住别人。

看这个组合：

| A→B | B→A | 该判什么？ |
|---|---|---|
| `NOT_EVALUATED`（计划里没给这条腿门限） | `RATE_FAIL`（RX 850 < 900） | ？ |

这次 A→B 的「判不了」只是**它自己的配置问题** —— 没配门限。
它一点都不说明 B→A 测出来的数不可信。

要是让它盖住，单元会显示「无法评价」，而 B→A 那个**确凿的不达标
从概览里消失了**。这是另一个方向的误判。

于是有了一张白名单：

```rust
pub const LEG_LOCAL_NOT_EVALUATED_CODES: [ReasonCode; 3] = [
    ReasonCode::ConfiguredLoadTooLow,   // 负载本来就没配够
    ReasonCode::OfferedLoadLow,          // 实际打出去的负载低
    ReasonCode::TargetMissing,           // 没给门限
];

fn blocks_other_legs(verdict: Verdict, reason_code: ReasonCode) -> bool {
    verdict == Verdict::NotEvaluated && !LEG_LOCAL_NOT_EVALUATED_CODES.contains(&reason_code)
}
```

注意那个 `!`：**这是白名单，不是黑名单。**

名单里的三个不盖住别人；**剩下的一律盖住**。新加一个原因码时不用改这里，
它自动按老行为走。白名单的默认值是保守的那一边 —— 这就是它比黑名单安全的地方。

真实项目的注释：

> 名单只放"确定安全"的三个，其余一律按老行为盖住：这里放宽一个码，
> 对应的就是一批历史上判「无法评价」的单元变成 `RATE_FAIL`。

**放宽一条规则的代价要能说清楚，说不清楚就别放宽。**

## 3. 第一条特例：`is_hard_single_udp_failure`

插了第 3 步之后，又出了新问题。

有些用例里，用户点名某个方向「必须灌通」。这个方向一个样本都没测到 ——
本质上是「工具没测出来」，但用户**指定**它算硬失败，判 `RATE_FAIL`。

现在看这个组合：

| A→B | B→A | 第 3 步之后判什么 |
|---|---|---|
| `RATE_FAIL`（单流 UDP 硬失败） | `NOT_EVALUATED`（采样覆盖率低） | `NOT_EVALUATED` ← 硬失败被吃掉了 |

用户点名必须灌通的方向没灌通，概览却显示「无法评价」。

所以硬失败要**排在**第 3 步前面：

```rust
pub const HARD_SINGLE_UDP_FAILURE_CODES: [ReasonCode; 2] = [
    ReasonCode::SingleUdpStreamFailed,
    ReasonCode::CtsSingleUdpStreamFailed,
];

pub fn is_hard_single_udp_failure(verdict: Verdict, reason_code: ReasonCode) -> bool {
    verdict == Verdict::RateFail && HARD_SINGLE_UDP_FAILURE_CODES.contains(&reason_code)
}
```

（教学版只有一个码，真实项目有两个 —— 另一个是 ctsTraffic 工具那条路径上
的同一件事。）

**为什么要同时看判定？** 只看原因码的话，一条带着这个码的 `NOT_EVALUATED`
会被当成硬失败，把整个单元拉成 `RATE_FAIL` —— 「没测成」被写成了
「性能不达标」，又绕回第 1 节那个误判方向去了。

## 4. 完整的九步

```text
1. 空集合                        → SETUP_ERROR
2. 任一 SETUP_ERROR              → SETUP_ERROR
3. 任一 硬失败                    → RATE_FAIL        ← 特例一
4. 任一 会盖住别人的 NOT_EVALUATED → NOT_EVALUATED    ← 特例二
5. 任一 RATE_FAIL                → RATE_FAIL
6. 任一 NOT_EVALUATED            → NOT_EVALUATED
7. 任一 MEASURED                 → MEASURED
8. 任一 SKIP                     → SKIP
9. 否则                          → PASS
```

两条特例的关系是**一层套一层**：

- 第 4 步防的是「环境异常被写成性能失败」
- 第 3 步是第 4 步的一个开口：这一种失败太重要，不许被盖

顺序反过来的话，第 3 步就形同虚设。**优先级列表里，每一行都是被某个
具体的缺陷推上去的。**

## 5. 动手

```bash
cp scaffold/aggregate_special.rs src/aggregate_special.rs
```

在 `src/lib.rs` 的模块列表里加一行（按字母序，放在 `builder` 前面）：

```rust
pub mod aggregate_special;
```

```bash
cargo test --lib aggregate_special      # 10 个测试，现在全红
```

三道题：

| 题 | 函数 | 提示 |
|---|---|---|
| 1 | `is_hard_single_udp_failure` | 两个条件都要满足 |
| 2 | `blocks_other_legs` | 白名单，注意那个 `!` |
| 3 | `aggregate_verdict_full` | 照抄 `verdict.rs` 的现有实现，在第 2、3 步之间插两步 |

**测试已经写好了。** 其中有一个特别值得看：

```rust
#[test]
fn 普通情形跟现有实现结果一样() { ... }
```

它拿五组普通输入，同时喂给新旧两个实现，要求结果一致。
特例只该在特定原因码上生效 —— 别的情况变了，那就不是「补两条特例」，
是「换了一套判定」。

> 加规则的时候，**证明你没改到别的地方**和证明新规则对，一样重要。

答案：`solutions/aggregate_special_answer.rs`（先自己写 15 分钟）。

## 6. 做完之后：搬进 verdict.rs

前面那步是在**隔离环境**里写的：新模块、新函数名，改坏了也影响不到别人。

现在把它搬进去，替掉 `src/verdict.rs` 里现有的 `aggregate_verdict`：

1. 把两个常量和两个函数搬进 `verdict.rs`
2. 把 `aggregate_verdict` 的函数体换成 `aggregate_verdict_full` 的
3. 删掉 `src/aggregate_special.rs` 和 `lib.rs` 里那一行
4. `cargo test`

**这一步才是真实工作的形状**：前面 103 个测试就是你的安全网。
挂了就读测试名 —— 它会直接告诉你破坏了哪条规则。

（`cargo test --test golden` 大概率也会红：判定变了，渲染出来的表就变了。
读一遍 diff，确认每一处变化都是你想要的，再 `UPDATE_GOLDEN=1`。）
