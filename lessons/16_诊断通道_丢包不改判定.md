# 第 16 课：诊断通道 —— 丢包 31% 为什么还是 PASS

**先决条件**：12 课做完。**和扩展课 13 / 14 没有先后关系。**

**目标**：理解 ADR-17 这条边界 —— 哪些信号可以改写判定，哪些只能进诊断。
这是这个项目里最反直觉、也最容易被人「顺手改掉」的一条规则。

## 1. 先跑

```bash
cargo run -- run fixtures/plan_loss.json output/loss.jsonl
```

```text
测试项                        实测速率      门限          结果
──────────────────────────────────────────────────────────────────
UDP 高丢包但速率达标          950 Mbps      900 Mbps      PASS
UDP 零丢包但速率不达标        850 Mbps      900 Mbps      RATE_FAIL
TCP 没采丢包                  950 Mbps      900 Mbps      PASS

总计 3 项：通过 2，未达标 1，无法评价 0

接下来该做什么：
  UDP 零丢包但速率不达标 → CPE 没跑到门限，检查信号、信道或设备本身

诊断（不影响判定）：
  UDP 高丢包但速率达标 → 丢包率 31.4%
```

**第一条丢了 31.4% 的包，判 PASS。第二条一个包没丢，判 RATE_FAIL。**

先别往下看，自己想一分钟：这合理吗？

## 2. 它合理，因为用例在问的不是那个问题

这个用例问的是：**「这条链路能不能跑到 900 Mbps？」**

第一条跑到了 950。所以答案是「能」。丢包 31% 解释了**为什么它只有 950 而不是
更高**，但不改变「它跑到了 900」这个事实。

第二条一个包没丢，稳稳地跑在 850 —— 就是跑不到 900。答案是「不能」。

> **吞吐验收的唯一判定输入是接收端 RX 平均对门限。**
> 这就是真实项目的 **ADR-17**。

`src/executor.rs` 里这段注释是原文：

```rust
// 丢包高是**排障线索**：它解释了为什么重传多、为什么时延抖，
// 但它不是这个用例要回答的问题。给它开第二条判定路径，
// 就等于让同一份报告里有两套「算不算失败」的口径。
```

## 3. 两条通道

```text
         测量到的东西
              │
     ┌────────┴────────┐
     │                 │
  RX 平均           丢包率 / 重传 / 负载下时延
     │                 │
     ▼                 ▼
  VerdictResult    VerdictResult
   .verdict         .diagnostics
  「算不算过」       「为什么会这样」
```

`VerdictResult` 上那个 `diagnostics: Vec<String>` 字段就是第二条通道。
它的注释写着：

```rust
/// **不参与判定**的排障线索。
///
/// 真实项目的 ADR-17：吞吐验收只认接收端 RX 平均，UDP 丢包、TCP 重传、
/// 负载下时延一律不许改写那个结论。但它们仍是排障必需的事实，所以单开
/// 一条通道，报告里显示成「诊断」。
```

**排障需要的事实 ≠ 判定需要的输入。** 混在一起的代价是：同一份报告里
出现两套「算不算失败」的口径，然后谁也说不清该信哪个。

## 4. 真实项目里这是一整类字段

去 `src/report/model.rs` 看 `Row`：

```rust
pub udp_loss: Option<f64>,
/// TCP 全程重传次数。与 `udp_loss` 平级：都是**只作诊断**的质量指标，
/// 都不参与判定（ADR-17）。
pub tcp_retransmits: Option<u64>,
pub load_latency: String,      // 负载下时延
pub ping_loss: Option<f64>,
pub tx_avg: Option<f64>,       // 发送端 TX 平均，也不参与判定
```

**不是一个特例，是一整类。** 认出这一类，读真实代码时就知道
哪些字段可以放心跳过 —— 它们不影响结论，只影响解释。

而这句话，是真实项目打给用户看的原文（`src/inner/mod.rs:1586`）：

```text
UDP_LOSS_HIGH: 丢包率 31.400% 超过门槛 1.000%；丢包只作诊断，达标与否只看接收端速率。
```

**把规则写进用户看得到的那句话里，比写在注释里管用得多** ——
下一个想「顺手让丢包判个 FAIL」的人，会先在报告里读到这句。

## 5. `None` 不是 0

```rust
pub udp_loss: Option<f64>,   // None = 没采到，不是「丢包 0%」
```

这是这一课的第二个点，比第一个更容易写错。

用 `f64` 的话，没采到丢包的那些行会静默变成 `0.0` —— 一份
「**全部零丢包**」的完美报告。没有任何报错，没有任何提示。

真实项目的原话（`src/inner/mod.rs:1580`）：

> 「UDP 丢包未知：两端都没拿到 receiver 汇总行；**丢包率按「不知道」处理，
> 不能当成 0%**。」

`fixtures/plan_loss.json` 第三条就是这个情况：没写 `udp_loss_ab`，读进来是
`None`，报告里那一格是空的 —— 空和 0 在报告里长得不一样，这是有意的。

```bash
cargo run -- csv output/loss.jsonl output/loss.csv
open output/loss.csv     # 看最后一列：空 vs 0.0
```

## 6. 「值不值得说」只有一份实现

```rust
pub fn loss_worth_mentioning(udp_loss: Option<f64>) -> bool {
    matches!(udp_loss, Some(v) if v > MAX_UDP_LOSS_PCT)
}
```

两个地方要问同一个问题：`executor`（写不写进 `diagnostics`）和
`report::render`（显不显示在摘要里）。

各写一遍 `loss > 1.0`，哪天门槛改成 2.0，两边就漂了 ——
报告里显示了一条诊断，JSONL 里却没有。

**这和第 07 课那条「判定只能有一份」是同一条规矩的小号版本。**
规矩不分大小：只要一个判断有两个消费者，它就该只有一份实现。

## 7. 动手任务

1. **把边界推倒试试**：在 `execute_leg` 里加
   `if leg.udp_loss > Some(10.0) { verdict.verdict = Verdict::RateFail; }`，
   跑 `cargo test`。看哪个测试红了、**读它的名字**。然后改回来。

2. 把 `Spec.udp_loss_ab` 的类型从 `Option<f64>` 改成 `f64`，跑
   `cargo test --lib plan`，看 `没采到丢包和丢包为零是两回事` 怎么红的。
   改回来。

3. 加一个 TCP 重传数：`Spec.tcp_retransmits_ab: Option<u64>` →
   `Leg` → `LegOutcome` → `Row`，超过 100 次就进诊断。
   **判定一个字节都不许动**，并写一个测试钉住这一点。
   （这一条走的就是第 12 课那条链路，但这次你知道终点该长什么样了。）

4. 把 `MAX_UDP_LOSS_PCT` 改成 `0.0`，跑 `fixtures/plan_loss.json`，
   看诊断栏变成什么样。想一想为什么真实项目把它做成了配置项。
