## 2. 它回答的是哪个问题

**「新版本比上一版差在哪。」** 版本验收只有这一个问题。

在有这张表之前，这个问题只能靠开两个窗口人眼比对几百行 ——
一次回归跑十几个小时，结论却卡在最后这一步。

数据侧的前提本来就齐了：`rows.jsonl` 是结构化的。**缺的只是一个消费它的出口。**
这一课的代码总共不到 200 行，但它把前面 11 课攒下来的东西变成了一个能交付的功能。

## 3. 对齐键：这一课真正的难点

两份报告，怎么知道哪一行对哪一行？

先想三种错误答案：

**❌ 按行号**（第 1 行对第 1 行）
两轮之间只要少跑或多跑一条，后面全体错位，于是每一行都被报成「变了」，
而实际什么都没变。

**❌ 按 `task_id`**
看着正好合适，它就是为了唯一标识一行而存在的。但它长这样：

```text
{plan_id}-{specs 下标}-r{轮次}
```

- `plan_id` 改一个字（换个计划名）→ 两轮一条都对不上
- 在 `specs` 中间插一条新规格 → 后面所有下标位移 → 全部报成「新增 + 缺失」

**真实项目栽的就是这个坑的另一个版本。** 它的 `Unit.id` 把网卡的**协商速率**
算进了身份 —— 这对断点续跑是对的（一条重新协商到 286 Mbps 的 Wi-Fi 链路不该
复用它在 2401 Mbps 时拿到的 PASS），但对**对比**恰恰相反：Wi-Fi 一重协商，
同一条测试在两轮里就成了两个 ID，整张表变成「全部新增 + 全部缺失」。
这是拿真实历史数据跑出来才发现的：两轮计划相同，却一条都对不上。

**✅ 自己拼一把只含不变条件的键**

```rust
pub fn comparison_key(row: &Row) -> String {
    format!("{}|{}|r{}", row.task, row.transport, row.round)
}
```

它回答的是「**这是不是同一个测试**」，而不是「这一轮的条件是不是和上一轮
完全一样」。**同一个字段，在「续跑」和「对比」两个用例里该不该算进身份，
答案是相反的。**

注意键里**不含门限**。门限从 900 提到 950 的时候，我们要看到的是
「同一条测试，门限变了所以判定变了」，而不是「旧的消失了 + 新增一条」。
这是个有取舍的选择 —— 真实项目把下发参数算进了键，因为它那边「参数变了就是
另一个测试」。读代码时要能分清哪些是**铁律**、哪些是**取舍**。

## 4. 判定翻转比数字变化更重要

```rust
if before.verdict == Verdict::Pass && after.verdict != Verdict::Pass {
    return DeltaKind::Regressed;
}
```

一条从 950 掉到 902 的链路（门限 900）和一条从 910 掉到 890 的，数字上差得
差不多，但后者跨过了门限。所以：**先看判定翻没翻，再看跌了多少。**

`DeltaKind` 的六个变体，声明顺序就是严重程度：

```rust
Regressed → SlowerButStillSameVerdict → Disappeared → Added → Fixed → Unchanged
```

`Ord` 是 derive 出来的，按变体的声明顺序比大小 —— 所以**调整变体顺序会直接改变
报告的排序**，不是无害的重排。这类「看起来只是整理代码」的改动最危险。

（rust-starter 第 15 课讲 `derive(Ord)` 时举的就是这个例子。
**声明顺序即行为，而编译器不会说话** —— 所以那个 enum 上面专门写了一行注释。）

### 一个和第 18 课直接相关的坑

`Disappeared` 的意思是「上一轮有、这一轮没有」。什么情况下会出现？

- 计划真的改了（删掉了一条 spec）—— 这是它该报的
- **上一轮跑到一半被人停了** —— 这是它**不该**报的

第二种要是也报成 `Disappeared`，读报告的人会以为计划变了，
或者以为程序出了 bug，**没有人会猜到那是因为有人点了停止**。

所以第 18 课那条规矩在这里收账：**被取消的单元照样出行，判定是 `SKIP`。**
于是对比时它们能正常对上，显示成「从 PASS 变成 SKIP」——
一眼就看出是没跑，不是消失了。

> 两课之间这个衔接值得记住：**上游少写一行，下游就多一个查不出的现象。**

## 5. 5% 那条线

```rust
pub const SIGNIFICANT_RATE_CHANGE: f64 = 0.05;
```

同一条链路连跑两次，网卡计数器口径下的差异通常在 1~2%。取 5% 是为了让这张表
**不刷屏** —— 把每一次 0.3% 的抖动都报成「下降」，等于没有这张表。

**动手**：把它改成 `0.001`，重跑对比，看那张表变成什么样。
然后想一想：一张「什么都报」的表和一张没有的表，区别在哪。

## 6. 计划不一样的时候

```rust
if !diff.same_plan {
    out.push_str("注意：两轮跑的不是同一份计划，「新增」和「缺失」说的是计划差异，不是设备表现。\n\n");
}
```

**计划不同不是错误**，只是意味着「不能比总数，只能逐条看」。
但这句话必须在最上面 —— 少了它，读的人会把计划差异当成设备回归。

```bash
cargo run -- compare output/before.jsonl output/rows.jsonl --plan-changed
```

## 7. 这张表本身也要钉住

对比报告的排序、分组、措辞，全是给人看的 —— 改一个字，下游读它的人就得重新适应。

`fixtures/golden/compare_v1_v2.txt` 存着它现在的样子，
`tests/golden.rs` 每次跑都逐字比对。改动是故意的就一行命令更新，是手滑就当场红。

细节在**第 20 课**。

## 8. 动手任务

1. 把 `DeltaKind` 里 `Regressed` 和 `Fixed` 的位置对调，跑 `cargo test`，
   看哪个测试红了、它的名字在说什么。改回来。
2. `comparison_key` 里加上门限（从 `param` 里取），跑
   `cargo test --lib compare`，看 `门限变了仍然对得上` 怎么红的。想清楚两种做法
   各适合什么场景，然后选一个留下 —— **并在注释里写明你选的理由**。
3. 给 `render` 加一列，显示门限（`UnitSnapshot.target_mbps` 已经有了）。
4. 让 `compare` 支持 `--only-regressed`：只显示判定变坏和速率下降的行。

**5（有点难）**：`same_plan` 现在要用户自己加 `--plan-changed` 说明。
真实项目靠 `Row` 上的 `plan_hash` 字段自动判断。给 `Row` 加上这个字段吧 ——
从 `plan.rs` 算一个哈希，经 `builder` → `executor` → `report` 传下来。

这条链路你在第 12 课走过一遍（那次传的是 `note`）。**这次是同一条路，
但这回它有个真实的用处。** 哈希不用密码学安全的，把
`plan_id + 每条 spec 的 title/transport/direction/target` 拼起来
逐字节 FNV-1a 就够。
