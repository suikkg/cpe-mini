# 第 02 课：核心判定规则

**目标**：读懂整个工具最要紧的那个函数，它只有十几行。

## 1. 先跑

```bash
cargo test --lib verdict
```

## 2. 读代码：`src/verdict.rs` 的 `rate_verdict`

```rust
pub fn rate_verdict(rx_avg: Option<f64>, target_mbps: f64, no_avg_code: ReasonCode) -> VerdictResult {
    let Some(avg) = rx_avg else {
        return VerdictResult::new(Verdict::NotEvaluated, no_avg_code, ...);
    };
    if target_mbps <= 0.0 {
        return VerdictResult::new(Verdict::Measured, ReasonCode::None, ...);
    }
    if avg >= target_mbps {
        VerdictResult::new(Verdict::Pass, ReasonCode::RxTargetMet, ...)
    } else {
        VerdictResult::new(Verdict::RateFail, ReasonCode::RxBelowTarget, ...)
    }
}
```

四条分支，覆盖全部情况：

| 输入 | 判定 | 原因码 |
|---|---|---|
| 没有可信平均 | `NotEvaluated` | 上游给的码 |
| 有平均，但没设门限 | `Measured` | `None` |
| 平均 ≥ 门限 | `Pass` | `RX_TARGET_MET` |
| 平均 < 门限 | `RateFail` | `RX_BELOW_TARGET` |

## 3. 三个必须理解的细节

**`let ... else`**

```rust
let Some(avg) = rx_avg else { return ...; };
```

意思是"能取出值就继续往下走，取不到就走 else 直接返回"。`else` 块必须以
`return` / `break` / `panic!` 结束。这是 Rust 里处理"提前退出"最干净的写法，
真实项目里到处都是。

**`>=` 不是 `>`**

刚好等于门限算通过。这一行写反，每次跑到临界值的设备都会被冤枉。
`tests::等于门限算通过` 专门钉住这件事。

**`NotEvaluated` 不是失败**

没测到数 ≠ CPE 不行。混在一起，用户会拿着一份"失败"报告去换设备，
而真正的问题是测试工具没起来。

## 4. 两个值得多看一眼的设计

**为什么 `no_avg_code` 是参数传进来的**

```rust
pub fn rate_verdict(rx_avg: Option<f64>, target_mbps: f64, no_avg_code: ReasonCode)
//                                                          ^^^^^^^^^^^ 上游给的
```

`rate_verdict` 知道「没有平均值 → 判 NOT_EVALUATED」，
但它**不知道为什么没有** —— 是一个样本都没采到？是有效窗口太短？
还是采样覆盖率太低？

那是 `rate_window` 才知道的事，所以由它算出来、一路传进来。

> **每一层只回答自己知道答案的那个问题。**
> 硬要让 `rate_verdict` 自己判断原因，就得把采样逻辑复制一份进来 ——
> 那正是这个项目一直在防的「两份实现最终一定会漂」。

**浮点数为什么敢用 `>=`**

```rust
if avg >= target_mbps { ... }
```

浮点数的老规矩是「别用 `==` 比」（`0.1 + 0.2 != 0.3`），但 `>=` 和 `<` 没这个问题 ——
它们只要求两个数分得出大小，不要求分毫不差。

这里真正要小心的是**另一件事**：`avg` 是几十个样本平均出来的，
它落在门限正上方还是正下方，本来就带着测量误差。
所以第 10 课会讲「有效窗口」—— 先保证这个平均值可信，比纠结比较符号重要得多。
